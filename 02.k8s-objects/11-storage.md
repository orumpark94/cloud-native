# 11. 데이터를 가진 앱을 Kubernetes 안에 둘 것인가

`cloud-native-learning-roadmap.md` 2단계. **새 실험을 하는 문서가 아니다.** 09(PV/PVC)와 10(StatefulSet)에서 실측한 것을 근거로 1단계에서 내린 결론 하나를 다시 판단한다.

---

## 0. 재검토 대상

1단계 장애 실험 문서에 이렇게 적혀 있다.

```text
결론    "데이터베이스는 Kubernetes 밖에 두는 편이 낫다"

근거    Pod 가 죽으면 데이터가 사라진다
```

그때의 상태를 정확히 적어두면 이렇다.

```text
PersistentVolume 이라는 게 있는 줄 몰랐다
StatefulSet 을 몰랐다
CSI 도 StorageClass 도 몰랐다
관측 도구가 없어 kubectl get 수준에서만 봤다
```

**결론을 낼 재료가 없는 상태의 판단이었다.** 이제 재료가 모였으니 다시 본다.

---

## 1. 근거는 무너졌다

### Pod 가 죽어도 데이터는 남는다

```text
[09 편 5절]
  PV 를 붙인 Pod 에 파일을 썼다
  Pod 를 지웠다 다시 만들었다
  → hello persistent 가 그대로 있었다

[Pod 편과 대비]
  컨테이너에 직접 쓴 index.html 은 Pod 를 지우니 사라졌다
```

### 재시작해도 자기 디스크를 다시 잡는다

```text
[10 편 9절]
  db-1 삭제 → db-1 로 재생성
  PVC 나이가 리셋되지 않았다 (5m45s → 6m28s)
  → 같은 PVC → 같은 PV → 같은 노드 → written by db-1 그대로
```

### 줄였다 늘려도 남는다

```text
[10 편 10절]
  replicas 3 → 1 → 3
  PVC 3개가 하나도 안 지워졌다 (기본값 Retain)
  → 다시 늘리니 원래 데이터로 복귀
```

### 전원을 강제로 끊어도 살아남았다

```text
[10 편 13절]
  worker02 Power Off → 다시 On
  → written by db-1 / worker02 / vol-c 그대로
```

**"데이터가 사라진다" 는 근거만 놓고 보면 이제 클러스터 안에 둬도 된다.**

---

## 2. 그런데 결론은 살아남았다 — 이유가 바뀌었다

실험에서 **1단계에서는 상상도 못 한 이유들**이 나왔다.

### 이유 1 — 노드가 죽으면 그 Pod 는 갈 곳이 없다

10 편 12절에서 실측한 것이다.

```text
0/3 nodes are available:
  1 node(s) didn't match PersistentVolume's node affinity,
  2 node(s) had untolerated taint(s).
```

```text
master01   taint      control-plane 이라 일반 Pod 를 안 넣는다
worker01   볼륨       그 디스크는 worker02 것이다
worker02   taint      죽어 있다
```

**강제로 지워도 Pending 이었다.** worker02 가 살아나기 전에는 방법이 없었다.

```text
09 에서 hostPath 가 데이터를 조용히 잃던 것을
nodeAffinity 로 막았다
그런데 같은 nodeAffinity 가 장애 때 이동을 막는다

"데이터가 있는 곳으로만 간다" 는 규칙 하나가
평상시엔 데이터를 지키고, 장애 시엔 발목을 잡는다
```

### 이유 2 — 아무도 알려주지 않는다

10 편 발견 27.

```text
db-1 이 6분째 멈춰 있는데 이벤트가 하나도 없다

"만들 수 없습니다" 도 없고
"노드가 죽어서 기다립니다" 도 없다
```

```text
알아차릴 방법
  kubectl get sts 의 READY 2/3 을 사람이 직접 보거나
  모니터링이 그 숫자를 지켜보고 있거나
```

**웹 서버라면 6분이면 Deployment 가 알아서 복구했다.** 같은 실험에서 web 4개는 정상으로 돌아왔다. 상태를 가진 쪽만 사람을 기다린다.

### 이유 3 — StatefulSet 만으로는 DB 가 되지 않는다

10 편 14절.

```text
[StatefulSet 이 해주는 것]
  자리(이름) / 사물함(볼륨) / 순서

[안 해주는 것]
  누가 마스터인지 정하기
  복제 설정 걸기
  마스터가 죽었을 때 복제본 승격 (failover)
  백업과 복구
  버전 업그레이드 시 데이터 마이그레이션
```

**우리가 만든 것은 사실 nginx 3개였다.** 이름만 db-0/1/2 였을 뿐이다.

```text
실제로 굴리려면 Operator 라는 층이 하나 더 필요하다
  Percona XtraDB Cluster Operator / Zalando Postgres Operator / Strimzi

Operator 는 CRD 위에 만들어진다 → 7단계 이후의 주제다
지금 우리가 쓸 수 있는 도구가 아니다
```

### 이유 3-B — 페일오버 지원은 DB 마다 다르다

"Operator 가 필요하다" 고 했는데, **얼마나 필요한지가 DB 마다 다르다.** 3단계에서 DB 를 고를 때 바로 쓸 판단 근거라 정리해 둔다.

#### 층이 셋이다

```text
[3층] Operator       Kubernetes 안에서 페일오버를 자동화하는 컨트롤러
[2층] DB 엔진 자체    PostgreSQL / MySQL 이 스스로 가진 기능
[1층] Kubernetes     아무것도 안 한다. DB 인지도 모른다
```

#### 2층이 갈린다

```text
                            복제      자동 승격(페일오버)
  PostgreSQL                있다      ✗ 없다      ← 외부 도구 필요
  MySQL (전통 복제)          있다      ✗ 없다      ← 외부 도구 필요
  MySQL Group Replication   있다      ✓ 있다      ← 엔진에 내장
  MongoDB (Replica Set)     있다      ✓ 있다      ← 엔진에 내장
  Kafka / Cassandra         있다      ✓ 있다
```

```text
[PostgreSQL]
  제공하는 것   스트리밍 복제. 마스터의 WAL 을 복제본이 받아 적용한다
  안 하는 것    마스터가 죽었는지 판단 / 누구를 승격시킬지 결정 / 승격 실행

  승격 명령 자체는 있다 (pg_ctl promote / SELECT pg_promote())
  그런데 "누가 언제 실행할지" 를 PostgreSQL 이 정하지 않는다
  → Patroni / repmgr / pg_auto_failover / Stolon 이 필요하다

[MySQL Group Replication]
  여러 노드가 합의 알고리즘으로 그룹을 이룬다
  마스터가 죽으면 남은 노드들이 투표해서 새 마스터를 뽑는다
  → 1단계에서 본 etcd 의 Raft 와 같은 발상이다
```

#### 승격이 끝이 아니다

```text
db-1 을 새 마스터로 승격시켰다
→ 그런데 앱은 아직 db-0 으로 접속하고 있다
→ 서비스는 여전히 안 된다
```

```text
[해결 1] Service 를 바꾼다
  마스터 Pod 에만 role=master 라벨을 붙인다
  Service 셀렉터가 그 라벨을 본다 → 승격 시 라벨을 옮긴다

[해결 2] 프록시를 둔다
  MySQL Router / HAProxy / PgBouncer
```

#### Patroni 는 Kubernetes API 를 쓴다 ★

```text
Patroni 는 "지금 누가 마스터인지" 를 어딘가에 기록해야 한다
  원래는 etcd 나 Consul 에 기록한다
  Kubernetes 위에서는 Kubernetes API 자체를 그 저장소로 쓸 수 있다
  → Endpoints 나 ConfigMap 에 적고, 승격 시 Service 대상을 갱신한다
```

**08(ServiceAccount/RBAC)에서 한 이야기가 여기서 실물이 된다.**

```text
[08 문서의 결론]
  "대부분의 Pod 는 Kubernetes API 와 얘기할 필요가 없다
   클러스터 정보를 다뤄야 하는 것만 필요하다"

[Patroni 가 정확히 그 경우다]
  ServiceAccount 가 붙고 Role 에 이런 권한이 들어간다
    endpoints    get / list / patch / update
    configmaps   get / list / create / patch
    pods         get / list / patch
  → 이 권한이 없으면 페일오버가 안 된다
  → 08 에서 만든 pod-reader 와 같은 구조다
```

#### 자동 페일오버가 위험한 이유 — 10 편과 같은 문제

```text
마스터와 복제본 사이의 네트워크만 끊겼다
→ 복제본이 "마스터가 죽었다" 고 판단하고 자기를 승격시킨다
→ 그런데 원래 마스터도 살아서 쓰기를 받고 있다
→ 마스터가 둘이다. 데이터가 갈라진다   (split-brain)
```

10 편에서 StatefulSet 이 대체 Pod 를 안 만든 이유와 정확히 같다. **저쪽이 진짜 죽었는지 알 수 없다.**

```text
그래서 제대로 된 도구는 정족수(quorum)를 쓴다
  노드를 홀수로 둔다 (3 / 5)
  과반이 모인 쪽만 마스터를 뽑을 수 있다
  → 갈라져도 한쪽만 살아남는다
```

**우리 클러스터의 제약이 여기서 걸린다.**

```text
worker 가 2대뿐이다
→ 복제본 3개를 서로 다른 노드에 못 둔다. 한 노드에 2개가 몰린다
→ 그 노드가 죽으면 정족수를 잃는다

학습에는 문제없지만 진짜 고가용성 구성은 안 된다
```

> 위 버전·도구 정보는 학습 데이터 기준이며 직접 돌려본 것이 아니다. Operator 생태계는 변화가 빠르므로 3단계에서 실제로 고를 때 공식 문서를 확인한다. Operator 별 비교는 7단계 이후(CRD)에서 다룬다.

### 이유 4 — 볼륨을 뭘 쓰든 대가가 있다

09 편 6절에서 정리한 것이다.

```text
[노드에 묶인 디스크 — local]
  빠르다. 네트워크를 안 탄다
  못 옮긴다. 노드가 죽으면 끝이다        ← 이유 1

[네트워크 스토리지 — NFS / Ceph / EBS]
  옮길 수 있다
  느리다. DB 처럼 디스크 성능이 중요한 것에는 부담이다
  EBS 는 AZ 를 못 넘는다. AZ 가 죽으면 같은 문제다
  그리고 우리 온프렘 클러스터에는 지금 아무것도 없다
```

## 3. 그래서 1단계 결론은 맞았나

**맞았다. 다만 이유가 달랐고, 절대 명제도 아니었다.**

```text
[1단계]
  "데이터가 사라지니까 밖에 둬라"
  → 근거가 틀렸다. 데이터는 지킬 수 있다

[지금]
  "데이터는 지킬 수 있다.
   문제는 그걸 지키려고 붙인 장치가 장애 때 발목을 잡고,
   그 위에 운영 층(Operator)이 또 필요하며,
   그 층을 감당할 수 있느냐가 관건이라는 것"
```

```text
바뀐 것은 판단의 성격이다
  [1단계]  기술적으로 불가능하다        → 사실이 아니었다
  [지금]   기술적으로는 가능하다
           운영 비용을 감당할 수 있느냐의 문제다   → 조건부 판단
```

## 4. 판단 기준

조건별로 나뉜다. 하나의 정답은 없다.

### 기준 1 — 앱이 스스로 복제하는가

```text
[한다 — Kafka / Cassandra / Elasticsearch / etcd]
  노드 하나 = 복제본 하나
  노드가 죽어도 나머지 복제본으로 서비스가 계속된다
  → local 볼륨이 오히려 맞다. 빠르고, 잃어도 하나뿐이다
  → "Kubernetes 가 아니라 앱이 고가용성을 책임진다"

  우리 클러스터의 etcd 가 이미 이 방식이다
  Static Pod 로 master01 의 로컬 디스크를 쓴다
  HA 구성에서는 3대를 둔다

[안 한다 — 단일 인스턴스 DB]
  노드가 죽으면 그대로 멈춘다
  → 네트워크 스토리지가 필요하다 (옮길 수 있어야 하니까)
  → 또는 클러스터 밖에 둔다
```

### 기준 2 — 스토리지 기반이 있는가

```text
[클라우드]
  EBS CSI / EFS / GCP PD 가 관리형으로 제공된다
  StorageClass 하나만 지정하면 된다
  → 클러스터 안에 두는 부담이 크게 줄어든다

[온프렘 — 지금 우리]
  StorageClass 가 없다 (09 편 2절 실측)
  Ceph 나 NFS 를 직접 구축해야 한다
  → 그 자체가 별도의 운영 대상이 된다
```

### 기준 3 — 운영 층을 감당할 수 있는가

```text
Operator 를 쓸 것인가
  → 그 Operator 자체를 운영해야 한다
  → 버전 업그레이드, 장애 시 동작 파악, CRD 이해

직접 만들 것인가
  → 백업 CronJob, 복구 절차, failover 스크립트를 전부 짠다

아니면 관리형에 맡길 것인가
  → RDS / Aurora / Cloud SQL
```

**팀 규모가 작을수록 마지막이 합리적이다.** 관리형 DB 가 비싼 게 아니라, 직접 운영하는 사람의 시간이 더 비싼 경우가 많다.

### 기준 4 — 잃으면 어떻게 되는가

```text
캐시 / 세션          잃어도 다시 만들면 된다  → 클러스터 안이 편하다
로그 / 메트릭        일부 유실을 감수한다     → 클러스터 안 (5단계 Prometheus)
사용자 데이터 / 결제  절대 못 잃는다          → 가장 보수적으로
```

### 표로

```text
                          클러스터 안        클러스터 밖
  앱이 스스로 복제한다        ✓ local 로        불필요
  단일 인스턴스              △ 네트워크 SC 필요  ✓
  클라우드                   ✓ CSI 있음        ✓ RDS
  온프렘 + SC 없음           ✗ 기반부터 만들어야  ✓
  절대 잃으면 안 되는 데이터   △ 백업 체계 필수    ✓
  학습이 목적                ✓ 직접 겪는 게 핵심  ✗
```

**마지막 줄이 이 프로젝트의 상황이다.**

## 5. 이 프로젝트에서는 어떻게 할 것인가

**단계별로 나눈다.** 3~6단계는 클러스터 안에서 직접 굴리고, 10단계에서 RDS 로 옮기며 무엇이 달라지는지 비교한다.

```text
[결정 근거]
  로드맵 원칙 1  자동화하기 전에 직접 구성한다
  로드맵 원칙 3  로컬에서 원리를 이해한 뒤 AWS 로 확장한다
                 AWS 가 대신 처리해주는 영역을 구분하는 것이 목적이다

  → "밖에 두는 게 낫다" 를 학습 단계에서 그대로 따르면
     정작 왜 그런지를 몸으로 알 기회가 없어진다
```

### 3~6단계 — 클러스터 안

```text
3단계   PostgreSQL 을 StatefulSet 으로
        local PV + nodeAffinity  (10 편 실험 B 그대로)
        앱은 Deployment

        추가로 만들어야 할 것
          백업 CronJob (pg_dump)          ← 13-job-cronjob.md 와 연결
          복구 절차 문서

4단계   GitOps 대상에 포함
        StatefulSet 과 PVC 를 Argo CD 가 관리할 때의 주의점
        → 볼륨을 가진 오브젝트를 선언적으로 다루는 것의 어려움

5단계   postgres_exporter 로 메트릭 수집
        → 10 편 발견 27 "아무도 안 알려준다" 를 여기서 해결한다
        → READY 숫자와 복제 지연을 Grafana 에 올린다

6단계   시나리오: DB 가 있는 노드를 죽인다
        → 10 편 12절을 실제 데이터로 재현한다
        → 이번엔 관측 지표가 있으므로 Incident Report 를 제대로 쓸 수 있다
```

### 10단계 — AWS 에서 RDS 로

```text
같은 애플리케이션을 RDS 에 붙인다
그리고 무엇이 사라지고 무엇이 생겼는지 비교한다

[사라지는 것]
  StatefulSet / PV / PVC / StorageClass
  백업 CronJob / 복구 절차
  노드 장애 시 수동 개입

[생기는 것]
  IAM / 보안 그룹 / 서브넷 그룹
  Terraform 으로 관리할 리소스가 늘어난다
  비용
  그리고 "장애가 나면 내가 할 수 있는 게 없다" 는 상황
```

### 지금 우리 클러스터의 제약을 명시해 둔다

```text
worker 가 2대뿐이다        복제본 3개를 서로 다른 노드에 못 둔다
StorageClass 가 없다       PV 를 손으로 만들어야 한다
control-plane 이 1대다     master01 이 죽으면 클러스터 전체가 멈춘다
백업 체계가 없다           지금 데이터가 날아가면 복구 방법이 없다
```

**3단계에서 DB 를 올릴 때 백업을 같이 만들어야 하는 이유가 마지막 줄이다.** 이걸 안 하면 "클러스터 안에 DB 를 뒀다" 가 아니라 "언제 잃어도 이상하지 않은 데이터를 뒀다" 가 된다.

## 6. 1단계 문장을 이렇게 고쳐 쓴다

```text
[1단계 원문]
  "데이터베이스는 Kubernetes 밖에 두는 편이 낫다"
  근거: Pod 가 죽으면 데이터가 사라진다

[고쳐 쓴 것]
  "Pod 가 죽어도 데이터는 남는다. 그건 PersistentVolume 이 해결한다.

   문제는 다른 데 있다.
     노드가 죽으면 그 Pod 는 갈 곳이 없고 (10 편 12절)
     그런데도 클러스터가 아무 말을 안 하며 (10 편 발견 27)
     StatefulSet 만으로는 마스터 승격도 백업도 안 된다 (10 편 14절)

   그래서 '밖에 둔다' 는 기술적 불가능이 아니라 운영 비용의 문제다.

   앱이 스스로 복제하면 안에 두는 게 낫고,
   단일 인스턴스이고 관리형 서비스를 쓸 수 있으면 밖이 낫다.
   온프렘에서 스토리지 기반부터 만들어야 한다면 밖이 낫다.

   다만 학습이 목적이면 안에 두고 직접 겪어야 한다."
```

## 정리

```text
[근거의 변화]
 1. "Pod 가 죽으면 데이터가 사라진다" 는 근거는 무너졌다
    PV / StatefulSet 으로 재시작·축소·전원차단을 전부 견뎠다
 2. 그런데 결론은 살아남았다. 이유가 완전히 달라졌다

[진짜 이유 넷]
 3. 노드가 죽으면 그 Pod 는 갈 곳이 없다 (강제 삭제해도 Pending)
    데이터를 지키려고 붙인 nodeAffinity 가 장애 때 발목을 잡는다
 4. 그런데 이벤트가 하나도 없다. 사람이 숫자를 직접 봐야 안다
 5. StatefulSet 은 자리와 사물함까지다
    마스터 선출 / 페일오버 / 백업은 Operator 의 몫이다
 6. 볼륨은 뭘 골라도 대가가 있다
    local 은 빠르지만 못 옮기고, 네트워크는 옮기지만 느리다

[판단 기준]
 7. 앱이 스스로 복제하는가 — 하면 local 이 오히려 맞다 (etcd 가 그 예다)
 8. 스토리지 기반이 있는가 — 클라우드는 CSI, 온프렘은 직접 구축
 9. 운영 층을 감당할 수 있는가 — Operator 도 운영 대상이다
10. 잃으면 어떻게 되는가 — 캐시와 결제 데이터는 다르게 판단한다

[성격의 변화]
11. 1단계  "기술적으로 불가능하다"      → 사실이 아니었다
    지금   "가능하다. 운영 비용의 문제다" → 조건부 판단

[이 프로젝트의 결정]
12. 3~6단계는 클러스터 안 StatefulSet, 10단계에서 RDS 로 옮겨 비교한다
13. 3단계에서 DB 와 함께 백업 CronJob 을 만든다
    지금 클러스터에는 백업 체계가 없다
14. 5단계 postgres_exporter 가 발견 27("아무도 안 알려준다")의 해답이다
15. 6단계 DB 노드 장애 실험이 10 편 12절의 실제 데이터 재현이다
```
