## 0. 공통 규칙

### 인증은 만들지 않는다

```text
X-User-Id: <숫자>     헤더로 사용자를 받는다. 검증하지 않는다
```

```text
[왜]
  로그인·회원가입을 만들면 3단계가 길어진다
  이 프로젝트에서 "사용자" 는 k6 다

[대신 문서에 남긴다]
  실제 서비스라면 여기에 인증이 들어간다
  4단계에서 Ingress 에 인증을 붙이는 실험을 할 수도 있다
```

### 에러 응답 형식을 하나로 통일한다

```json
{
  "error": {
    "code": "OUT_OF_STOCK",
    "message": "재고가 부족합니다",
    "detail": { "book_id": 1, "requested": 3, "available": 1 }
  }
}
```

```text
[왜 통일하나]
  5단계에서 에러를 code 별로 세려면 형식이 같아야 한다
  → "재고 부족" 과 "DB 연결 실패" 를 지표에서 구분할 수 있다

  형식이 제각각이면 "500이 늘었다" 이상을 말할 수 없다
```

### 모든 응답에 요청 ID 를 붙인다

```text
X-Request-Id: <uuid>
```

```text
[왜]
  요청이 API → Redis → PostgreSQL → 큐 → Worker 로 흐른다
  장애가 났을 때 "이 요청이 어디서 멈췄나" 를 추적하려면 공통 키가 필요하다

  클라이언트가 보내면 그대로 쓰고, 없으면 만든다
  로그와 응답 헤더 양쪽에 남긴다
```

**5단계에서 로그를 모을 때 이게 없으면 추적이 불가능하다.**

### 상태 코드를 쓰는 기준

```text
200  정상
202  접수했다. 아직 처리 안 됐다          ← 주문
400  요청이 잘못됐다 (형식)
404  없는 자원이다
409  지금은 안 된다 (재고 부족)           ← 재시도해도 안 될 수 있다
429  너무 많이 보냈다                    (지금은 안 씀. 6단계에서 넣을 수도)
500  서버 잘못이다
503  의존하는 것이 죽었다                ← DB / Redis 장애
```

```text
[500 과 503 을 나누는 이유]
  500  우리 코드의 버그다. 재시도해도 똑같다
  503  밖의 문제다. 잠시 뒤 재시도하면 될 수 있다

  → 5단계에서 이 둘을 나눠 보면 원인 판단이 빨라진다
```

## 2. GET /books — 책 목록

```text
GET /books?limit=20&offset=0
```

### 응답 200

```json
{
  "items": [
    { "id": 1, "title": "책 제목", "price": 15000, "stock": 3 }
  ],
  "limit": 20,
  "offset": 0,
  "total": 137
}
```

### 필드를 이만큼만 두는 이유

```text
[남기는 기준]  이 필드가 어떤 실험을 가능하게 하는가

  stock   재고 판단 → 동시성 실험 (경로 2 가 존재하는 이유)   ★
  price   주문 금액 계산
  title   사람이 읽을 이름
```

```text
author / isbn / publisher / 표지 이미지 …
  → 아무 실험도 만들지 않는다 → 넣지 않는다

데이터를 늘리면 "실제 앱처럼" 보이지만 장애 실험에는 도움이 안 된다
```

### limit / offset / total — 잘라서 주기

```text
limit    몇 개를 줄까          20개만
offset   몇 개를 건너뛸까       앞의 40개는 건너뛰고
total    전체가 몇 개인가       다 합치면 137개
```

```text
전체 137권

  [1 2 3 ... 20] [21 ... 40] [41 ... 60] ...
   offset=0        offset=20   offset=40
```

```text
SELECT id, title, price, stock FROM books ORDER BY id LIMIT 20 OFFSET 40;
SELECT COUNT(*) FROM books;
```

```text
[왜 잘라 주나]
  전부 주면 응답이 수십 MB 가 되고 DB 가 전체를 읽는다
  → 한 번의 요청이 서버를 마비시킨다
```

### 그런데 이게 실험 재료다 ★

```text
[offset 이 커지면 느려진다]
  OFFSET 40      앞의 40행을 읽고 버린다      빠르다
  OFFSET 50000   앞의 5만 행을 읽고 버린다     느리다

  DB 는 "41번째부터" 로 바로 못 간다. 앞의 것을 세면서 지나간다
```

**`/debug/slow-query` 를 안 써도 진짜 느린 쿼리가 생긴다.**

```text
[6단계 실험]
  k6 로 offset 이 큰 요청을 섞는다
  → DB CPU 와 응답 시간이 오르는 걸 본다
  → "왜 특정 요청만 느린가" 를 지표로 찾는다
  → 그러려면 지표에 offset 구간이 남아야 한다   (05-metrics.md 에서 다룬다)
```

```text
[COUNT(*) 도 비용이다]
  total 을 구하려고 매번 전체를 센다
  → 행이 많으면 이것만으로 느리다

  실무 해법은 대략치 / 캐시 / 아예 안 주기다
  → 지금은 그냥 센다. 느려지는 걸 본 뒤에 판단한다
```

### 캐시

```text
키       books:list:{limit}:{offset}
TTL      60초
```

```text
[동작]
  1. Redis 에서 찾는다
  2. 있으면 그대로 준다                          캐시 적중
  3. 없으면 PostgreSQL 에서 읽는다                캐시 미스
  4. Redis 에 저장한다 (실패해도 무시)
  5. 준다
```

### 설계 판단 — `stock` 을 목록에 넣을 것인가 ★

```text
[문제]
  재고는 주문할 때마다 바뀐다
  그런데 목록은 60초 캐시된다
  → 캐시된 목록의 재고는 최대 60초 낡은 값이다
```

```text
[선택지]
  A. 목록에서 stock 을 뺀다. 상세에서만 보여준다
  B. 넣되 "참고용" 으로 둔다. 주문 시점에 다시 확인한다

[선택 — B]
  실제 쇼핑몰이 그렇게 한다. 목록의 재고는 참고값이다
  그리고 "캐시된 값이 낡았다" 는 상황 자체가 실험 재료다
  → 6단계에서 "목록엔 재고가 있는데 주문하면 409" 를 만들 수 있다
```

**최종 판단은 언제나 경로 2(동기 쓰기)에서 한다.** 캐시는 판단 근거가 아니다.

### Redis 가 죽었을 때

```text
Redis 연결 실패 → 무시하고 PostgreSQL 에서 읽는다 → 200 을 준다
```

```text
[왜 503 이 아닌가]
  캐시는 "있으면 좋은 것" 이다. 없어도 동작해야 한다
  → 11편의 판단 기준: 잃어도 되는 데이터

[대신 지표에 남긴다]
  cache_errors_total 을 올린다
  → 5단계에서 "느려진 원인이 캐시 장애" 임을 알 수 있다
```

### PostgreSQL 이 죽었을 때

```text
503  { "error": { "code": "DB_UNAVAILABLE" } }
```

## 4. POST /orders — 주문 접수 ★

이 앱에서 가장 중요한 엔드포인트다. **경로 2와 3을 모두 지난다.**

```text
POST /orders
X-User-Id: 1
Content-Type: application/json

{ "book_id": 1, "quantity": 2 }
```

### 응답 202 Accepted

```json
{
  "order_id": 42,
  "status": "pending",
  "book_id": 1,
  "quantity": 2,
  "total_price": 30000,
  "created_at": "2026-08-25T10:00:00+09:00"
}
```

```text
Location: /orders/42
```

```text
[왜 201 이 아니라 202 인가]
  201 Created  "만들었고 처리도 끝났다"
  202 Accepted "접수했다. 처리는 아직이다"

  우리는 재고만 확보하고 결제 처리는 Worker 에게 넘긴다
  → 202 가 맞다

  → 이걸 201 로 주면 클라이언트가 "끝났다" 고 오해한다
```

### 처리 순서

```text
[경로 2 — 동기]
  1. 요청 형식을 검증한다                       실패 → 400
  2. 트랜잭션을 연다
  3. 책을 조회한다 (행 잠금)                     없음 → 404
  4. 재고를 확인한다                            부족 → 409
  5. 재고를 차감한다
  6. 주문을 status=pending 으로 저장한다
  7. 커밋한다

[경로 3 — 비동기]
  8. Redis 큐에 주문 ID 를 넣는다                실패 → 아래 참조
  9. 202 를 준다
```

### 8번이 실패하면 — 설계 판단 ★★

```text
재고는 이미 차감됐는데 큐 등록에 실패했다
```

```text
[선택지]
  A. 주문을 취소한다 (재고 복구) → 503 을 준다
     사용자는 실패를 안다. 재고도 원래대로다

  B. 202 를 준다. 큐 등록 실패는 로그만 남긴다
     주문은 받았는데 영원히 처리되지 않는다
```

**A 를 선택한다.**

```text
[이유]
  B 는 "조용한 실패" 다
  2단계 내내 그것 때문에 고생했다
    볼륨은 Bound 인데 데이터가 없었다
    Pod 가 멈췄는데 이벤트가 없었다
    DaemonSet 이 0개인데 지표가 정상이었다
    백업이 실패했는데 아무도 몰랐다

  → 이 앱에서는 만들지 않는다
```

```text
[구현 방식]
  큐 등록까지 성공해야 커밋한다
  즉 7번(커밋)을 8번 뒤로 옮긴다

  1~6  트랜잭션 안에서
  7    Redis 큐에 넣는다
  8    성공하면 커밋 / 실패하면 롤백 + 503
```

```text
[그런데 이것도 완벽하지 않다]
  큐에는 들어갔는데 커밋 직전에 프로세스가 죽으면?
  → 큐에는 있는데 DB 에는 주문이 없다
  → Worker 가 그 ID 를 찾다가 실패한다

  분산 트랜잭션의 근본 문제다. 여기서는 해결하지 않는다
  대신 Worker 가 "없는 주문" 을 만나면 조용히 버리고 지표를 올린다
  → 6단계에서 이 상황을 일부러 만들어본다
```

**모순을 숨기지 않고 문서에 남긴다.**

### 응답 409 — 재고 부족

```json
{
  "error": {
    "code": "OUT_OF_STOCK",
    "message": "재고가 부족합니다",
    "detail": { "book_id": 1, "requested": 2, "available": 1 }
  }
}
```

```text
[왜 400 이 아니라 409 인가]
  400  요청 자체가 잘못됐다. 고쳐서 다시 보내라
  409  요청은 맞는데 지금 상태와 충돌한다

  재고는 시간이 지나면 바뀔 수 있다 → 409 가 맞다
```

### 응답 503 — 의존 서비스 장애

```json
{ "error": { "code": "DB_UNAVAILABLE" } }
{ "error": { "code": "QUEUE_UNAVAILABLE" } }
```

### 정하지 않은 것 — 멱등성

```text
[문제]
  클라이언트가 타임아웃으로 재시도하면 주문이 두 번 들어간다

[실무 해법]
  Idempotency-Key 헤더를 받아 중복을 걸러낸다

[지금은 안 한다]
  구현이 늘어난다
  그리고 6단계에서 "네트워크 지연으로 중복 주문이 생기는" 실험을
  해볼 여지를 남겨둔다
```

## 5. GET /orders/{id} — 주문 처리 상태

```text
GET /orders/42
X-User-Id: 1
```

### 응답 200

```json
{
  "order_id": 42,
  "user_id": 1,
  "book_id": 1,
  "quantity": 2,
  "total_price": 30000,
  "status": "completed",
  "created_at":   "2026-08-25T10:00:00+09:00",
  "started_at":   "2026-08-25T10:00:03+09:00",
  "finished_at":  "2026-08-25T10:00:05+09:00",
  "failure_reason": null
}
```

### status 값

```text
pending      접수됐다. 큐에 있다
processing   Worker 가 처리 중이다
completed    끝났다
failed       실패했다. 재고는 복구됐다
```

```text
[시각을 셋 다 남기는 이유]
  created_at   접수 시각
  started_at   Worker 가 집어든 시각
  finished_at  처리를 끝낸 시각

  created → started    큐에서 기다린 시간   ← 적체를 재는 값 ★
  started → finished   실제 처리 시간

  두 값이 섞여 있으면 "느리다" 의 원인을 못 찾는다
```

**13편에서 본 그 문제와 같다.** Job 의 `DURATION` 에 이미지 받는 시간이 섞여 있어 실제 작업 시간을 알 수 없었다.

### 캐시하지 않는다

```text
[왜]
  주문 상태는 계속 바뀐다
  낡은 값을 주면 사용자가 "처리 중" 을 계속 본다
  → 이건 잃어도 되는 데이터가 아니다
```

## 10. 응답 시간의 목표값

**지금 정하지 않는다.**

```text
[왜]
  아직 아무것도 안 재봤다
  "200ms 이내" 같은 숫자를 지금 정하면 근거 없는 목표가 된다

[언제 정하나]
  5단계에서 정상 상태의 분포를 먼저 잰다
  그다음 "이 값을 넘으면 이상하다" 를 정한다
  → 그게 알람 임계값이 된다
```

**측정이 목표보다 먼저다.**

## 정리 — 이 문서에서 내린 판단

```text
 1. 인증은 만들지 않는다. X-User-Id 헤더로 대신한다
 2. 에러 응답 형식을 통일한다 → 5단계에서 code 별로 셀 수 있게
 3. X-Request-Id 로 요청을 추적한다 → 여러 구성요소를 잇는 유일한 키
 4. 500(우리 잘못)과 503(밖의 문제)을 나눈다
 5. 목록에 stock 을 넣되 참고값으로 둔다. 판단은 주문 시점에 한다
 6. 주문은 202 다. 201 이 아니다
 7. 큐 등록이 실패하면 롤백하고 503 을 준다 ★
    조용한 실패를 만들지 않는다
 8. 커밋 직전 프로세스 사망은 해결하지 않는다. 문서에 남기고 6단계에서 겪는다
 9. 주문에 시각을 셋 남긴다 → 대기 시간과 처리 시간을 분리해서 재려고
10. ready 응답에 무엇이 실패했는지 적는다
11. 응답 시간 목표는 지금 정하지 않는다. 재보고 정한다
12. 책 필드는 id / title / price / stock 넷뿐이다
    "어떤 실험을 가능하게 하는가" 를 기준으로 남겼다
13. 페이지네이션은 유지한다. 단순해 보이지만 실험 재료다
    offset 이 커지면 느려진다 → 진짜 느린 쿼리를 만들 수 있다
```
