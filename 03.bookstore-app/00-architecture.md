# 00. 아키텍처 — 세 갈래 경로

3단계 첫 문서. **무엇을 만들지가 아니라 왜 이렇게 나눴는지**를 남긴다.

---

## 1. 전체 그림

```text
                        Client (k6 / curl)
                              │
                              ▼
                        Ingress  (4단계에서 설치)
                              │
                              ▼
                    ┌─────────────────┐
                    │   Backend API   │   Deployment
                    │    (FastAPI)    │   상태 없음. 여러 개 띄운다
                    └────────┬────────┘
             ┌───────────────┼───────────────┐
             ▼               ▼               ▼
        ┌─────────┐    ┌──────────┐   ┌──────────────┐
        │  Redis  │    │PostgreSQL│   │    Redis     │
        │ (캐시)   │    │  (원본)   │   │   (큐)       │
        └─────────┘    └──────────┘   └──────┬───────┘
                            ▲                │
                            │                ▼
                            │         ┌─────────────┐
                            └─────────│   Worker    │  Deployment
                                      │  (FastAPI 밖)│  큐를 소비한다
                                      └─────────────┘
```

```text
Redis 는 한 대다. 캐시와 큐를 같이 쓴다
  → 6단계에서 Redis 를 죽이면 두 경로가 동시에 무너진다
  → 그게 연쇄 장애 실험의 재료다

실무에서는 보통 나눈다. 나누는 이유도 6단계에서 몸으로 알게 된다
```

---

## 2. 경로가 셋이다 ★

**이 앱의 핵심 설계다.** 성격이 다른 세 경로를 일부러 만들었다.

```text
[경로 1] 읽기        GET /books, GET /books/{id}
                    Redis 캐시 → 없으면 PostgreSQL → 캐시에 저장

[경로 2] 동기 쓰기    POST /orders 의 앞부분
                    PostgreSQL 트랜잭션으로 재고 확인·차감

[경로 3] 비동기 처리  POST /orders 의 뒷부분 + Worker
                    Redis 큐에 넣고 즉시 응답 → Worker 가 나중에 처리
```

### 왜 셋으로 나눴나

```text
[하나였다면]
  모든 요청이 같은 성격이다
  → 지표가 뭉친다. "느려졌다" 이상을 말할 수 없다
  → 장애를 일으켜도 전부 똑같이 실패한다

[셋이면]
  "조회는 멀쩡한데 주문만 실패한다"
  "주문 접수는 되는데 처리가 안 된다"
  → 부분 장애를 만들 수 있고, 지표로 구분할 수 있다
```

**2단계에서 "조용한 실패" 를 네 번 겪었다.** 그때 문제는 "무엇을 봐야 할지 몰랐다" 는 것이었다. 경로를 나눠두면 **볼 것이 미리 정해진다.**

## 3. 경로 1 — 읽기

```text
GET /books
GET /books/{id}
```

```text
1. Redis 에서 찾는다
2. 있으면 그대로 준다                    (캐시 적중)
3. 없으면 PostgreSQL 에서 읽는다          (캐시 미스)
4. 결과를 Redis 에 저장한다 (TTL 60초)
5. 준다
```

### 이 경로가 만드는 실험

```text
[정상]      요청의 대부분이 캐시에서 나간다. DB 는 한가하다

[Redis 를 죽인다]
  → 캐시 적중률이 0% 가 된다
  → 모든 요청이 DB 로 간다
  → DB 커넥션 풀이 고갈된다
  → 조회도 주문도 전부 멈춘다              ★ 연쇄 장애

  "캐시 하나 죽었을 뿐인데 전체가 멈췄다"
```

```text
[재발 방지책을 하나씩 넣어보고 지표로 확인한다]
  DB 커넥션 풀 상한
  Redis 장애 시 회로 차단
  캐시 미스 시 요청 병합
```

**이게 실무에서 가장 흔하고 무서운 장애 유형이다.** 안전하게 재현해볼 수 있다.

### 설계 판단

```text
[캐시가 없으면 어떻게 되나]
  느려지지만 동작은 한다 → 그래서 Redis 는 "있으면 좋은 것" 이다
  → 11편의 판단 기준을 적용하면 Redis 는 잃어도 되는 데이터다
  → StatefulSet 이 아니라 Deployment 로 띄운다

[TTL 60초를 고른 이유]
  실험 중에 캐시 효과를 눈으로 보려면 짧아야 한다
  운영이라면 훨씬 길게 잡는다
```

## 4. 경로 2 — 동기 쓰기 (재고)

```text
POST /orders  의 앞부분
```

```text
1. 트랜잭션을 연다
2. 그 책의 재고를 읽는다 (행 잠금)
3. 부족하면 409 를 준다
4. 재고를 차감한다
5. 주문을 status=pending 으로 저장한다
6. 커밋한다
```

### 왜 재고만 동기인가

```text
[비동기로 하면]
  주문을 일단 받는다 → 나중에 "재고가 없습니다" 라고 취소한다
  → 사용자 경험이 나쁘다

[동기로 하면]
  즉시 판단한다. 안 되면 바로 안 된다고 한다
  시간이 오래 걸리는 처리만 뒤로 미룬다
```

**실무의 일반적인 방식이기도 하다.**

### 이 경로가 만드는 실험 ★

```text
[재고 경쟁]
  책 재고 1권. 사용자 둘이 동시에 구매
  API Pod 가 2개면 각각 다른 Pod 가 처리한다
  → 둘 다 "재고 1권" 을 읽고 둘 다 팔면?
  → 재고가 -1 이 된다
```

```text
[여기서 배우는 것]
  "Pod 를 늘리면 해결된다" 가 틀린 경우가 있다
  → Deployment replicas 를 늘렸더니 데이터가 깨졌다
  → 상태 없는 앱이라도 공유 자원에는 조율이 필요하다
```

```text
[해결책을 비교한다]
  DB 행 잠금 (SELECT ... FOR UPDATE)   느리지만 확실하다
  Redis 원자적 카운터                   빠르지만 DB 와 어긋날 수 있다
  → 각각의 대가를 지표로 확인한다
```

### 설계 판단 — 처음에는 일부러 잠금 없이 만든다

```text
1차   잠금 없이 만든다 → 부하를 넣어 재고를 음수로 만든다
2차   잠금을 넣는다 → 음수가 안 나오는지 확인한다
      대신 처리량이 얼마나 떨어지는지 잰다
```

**"실패한 출력 자체가 학습 대상" 이라는 1단계 원칙 그대로다.**

## 5. 경로 3 — 비동기 처리

```text
POST /orders  의 뒷부분
7. Redis 큐에 주문 ID 를 넣는다
8. 202 Accepted 로 응답한다        ← 사용자는 기다리지 않는다

Worker
  큐에서 꺼낸다
  → 결제 처리를 흉내낸다 (지연 + 확률적 실패)
  → 성공: status=completed
  → 실패: status=failed + 재고 복구
```

### 왜 이 구조가 필요한가

**로드맵 6단계가 이걸 전제한다.**

```text
"요청 수는 폭증했으나 각 요청이 가벼움 → CPU 는 거의 안 오름"

3단계에서 만든 애플리케이션이 정확히 이 상황을 만들 수 있도록 설계되어 있다
API → Redis Queue → Worker → PostgreSQL 구조는 전 구간이 I/O 중심이다
```

```text
[CPU 를 안 쓰는데 느려지는 상황을 만들 수 있다]
  → "CPU 사용률만 보면 아무 문제가 없어 보인다"
  → 그런데 사용자는 응답을 못 받는다
  → 무엇을 봐야 하는가 = 5단계의 질문
```

### 이 경로가 만드는 실험

```text
[큐 적체]
  Worker 를 1개로 줄이고 부하를 넣는다
  → 큐 길이가 계속 늘어난다
  → 주문 접수는 여전히 성공한다 (202)
  → 그런데 아무것도 처리되지 않는다

  "API 는 정상입니다" 라고 말할 수 있는가?
```

```text
[볼 지표]
  큐 길이           지금 몇 개가 밀려 있나
  입력 속도         초당 몇 개가 들어오나
  소비 속도         초당 몇 개가 처리되나
  → 입력 > 소비 가 지속되면 언젠가 터진다
```

```text
[Worker 실패와 보상]
  결제가 실패하면 재고를 되돌려야 한다
  → 되돌리는 도중에 Worker 가 죽으면?
  → 재고가 안 돌아온 채로 남는다
  → 이것도 실험 대상이다
```

### 설계 판단 — Worker 를 별도 Deployment 로

```text
[API 안에서 백그라운드로 돌리면]
  API Pod 를 늘리면 Worker 도 같이 늘어난다
  → 따로 조절할 수 없다
  → "Worker 만 줄여서 큐를 밀리게 하는" 실험이 불가능하다

[별도 Deployment 면]
  API 3개 / Worker 1개 같은 조합이 가능하다
  → 병목을 원하는 곳에 만들 수 있다
```

**같은 이미지를 쓰되 실행 명령만 다르게 한다.** 빌드를 두 번 하지 않는다.

## 6. 상태를 가진 것과 없는 것

11편에서 정리한 판단 기준을 적용한다.

| 구성요소 | 상태 | 배치 | 잃으면 |
|---|---|---|---|
| API | 없음 | Deployment | 아무 일 없음. 다른 Pod 가 받는다 |
| Worker | 없음 | Deployment | 처리가 멈춘다. 큐는 남아 있다 |
| Redis (캐시) | 잃어도 됨 | Deployment | 느려진다. DB 로 몰린다 ★ |
| Redis (큐) | **잃으면 안 됨** | 같은 Redis | **접수된 주문이 사라진다** ★★ |
| PostgreSQL | 잃으면 안 됨 | StatefulSet + PV | 전부 멈춘다 |

### 여기 모순이 하나 있다 ★

```text
캐시로서의 Redis    잃어도 된다
큐로서의 Redis      잃으면 안 된다

그런데 같은 Redis 다
```

```text
[그래서 어떻게 할 것인가]
  A. Redis 에 영속성을 켠다 (AOF/RDB) → StatefulSet + PV 로 바꾼다
  B. 큐를 PostgreSQL 로 옮긴다 → Redis 는 순수 캐시로
  C. 그냥 둔다. 잃으면 잃는 대로 실험한다

[이 프로젝트의 선택 — C 로 시작한다]
  6단계에서 Redis 를 죽여 "접수된 주문이 사라지는" 상황을 직접 겪는다
  그다음 A 나 B 로 바꾸고 무엇이 달라지는지 비교한다
```

**모순을 미리 없애지 않는다.** 겪어봐야 왜 실무에서 큐와 캐시를 나누는지 안다.

## 7. 요청이 흐르는 모습

### 정상 — 책 조회

```text
GET /books/1
  → API
  → Redis GET book:1
  → 있음
  → 200 OK                              (2ms)
```

### 정상 — 주문

```text
POST /orders {book_id: 1, quantity: 1}
  → API
  → PostgreSQL 트랜잭션 (재고 확인·차감, 주문 저장)
  → Redis LPUSH order_queue 42
  → 202 Accepted {order_id: 42, status: "pending"}   (15ms)

  ... 잠시 후 ...

Worker
  → Redis BRPOP order_queue
  → 42 를 꺼낸다
  → 결제 처리 (0.5~2초)
  → PostgreSQL UPDATE status='completed'
```

```text
GET /orders/42
  → 200 OK {status: "completed"}
```

### 장애 — Redis 가 죽었을 때

```text
GET /books/1
  → Redis 연결 실패
  → PostgreSQL 에서 읽는다                (느리다)
  → 캐시 저장 실패는 무시한다
  → 200 OK                              (80ms → 부하가 늘면 급격히 악화)

POST /orders
  → 재고 차감은 성공한다                   ← DB 는 살아 있으니까
  → Redis LPUSH 실패
  → 여기서 어떻게 할 것인가?              ★ 설계 판단이 필요한 지점
```

```text
[선택지]
  A. 500 을 준다. 트랜잭션도 롤백한다
     → 사용자는 주문 실패를 안다. 재고도 안 깎인다
  B. 202 를 준다. 큐 등록 실패는 로그만 남긴다
     → 주문은 받았는데 영원히 처리 안 된다   ← 최악이다

[이 프로젝트의 선택 — A]
  "조용한 실패" 를 만들지 않는다. 2단계 내내 그것 때문에 고생했다
```

## 8. 이 구조로 만들 수 있는 장애

로드맵 3단계가 나열한 목록과 대조한다.

| 로드맵이 요구한 장애 | 이 앱에서 만드는 방법 |
|---|---|
| API Pod 장애 | Deployment replica 를 죽인다 |
| Redis 연결 장애 | Redis Pod 를 죽인다 → 캐시 미스 + 큐 정지 |
| PostgreSQL 연결 장애 | StatefulSet 을 죽인다 |
| Worker 처리 지연 | 환경변수로 처리 시간을 늘린다 |
| Queue 적체 | Worker 를 1개로 줄이고 부하를 넣는다 |
| DB 응답 지연 | `/debug/slow-query` 로 느린 쿼리를 만든다 |
| Connection Pool 고갈 | Redis 를 죽여 DB 로 몰아넣는다 ★ |
| 메모리 누수 | `/debug/leak` 로 메모리를 잡아둔다 |
| CPU 과부하 | `/debug/burn` 으로 CPU 를 태운다 |
| 잘못된 환경변수 | ConfigMap 에 오타를 낸다 (06편의 그것) |
| Readiness 실패 | `/debug/toggle-ready` 로 강제 실패시킨다 |
| 부분 장애 | 조회는 되는데 주문만 안 되는 상황을 만든다 |

**전부 커버된다.** 마지막 "부분 장애" 는 경로를 셋으로 나눴기 때문에 가능하다.

## 9. 설계에서 미리 정하지 않은 것

```text
1. 재고 잠금 방식
   → 일부러 없이 시작한다. 깨지는 걸 본 뒤에 넣는다

2. Redis 를 캐시와 큐로 나눌지
   → 하나로 시작한다. 6단계에서 문제를 겪은 뒤 판단한다

3. DB 커넥션 풀 크기
   → 기본값으로 시작한다. 5단계에서 지표를 보고 정한다

4. Worker 개수와 처리 시간
   → 환경변수로 뺀다. 실험할 때마다 바꾼다
```

**미리 최적화하지 않는다.** 왜 그 값이어야 하는지를 지표로 설명할 수 있을 때 정한다.
